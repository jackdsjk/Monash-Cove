## 1. 摘要

Cove 是一款面向 Monash 学生的本地优先信息工具。它在后台巡检 Moodle、Ed、学校邮箱和 OnTrack，只报告“自上次查看以来变了什么”，不替用户判断“什么重要”。

判断权归用户。系统只陈述可核对的事实——新增、截止日改动、成绩发布、新文件、新帖与回复——按可核对的事实排序，最多给 3 条带理由的“建议先看”。系统解析不了的原文段落单独归入“未能识别”，默认可见。

当前状态：四个来源已能真实读取并同步；本地 Web App 有 9 个页面可用；另有 Electron 桌面壳（未签名）和 55 条样本的匿名演示原型。**简报页仍是旧的“系统分类”模型**（必须处理 / 待确认 / 已折叠），是本版要改的主要部分。

## 2. 定位与原则

**定位：**跨平台巡检 + 变更归集 + 证据回链。

相邻产品能复制“聚合通知”，复制不了两件事：每条判断都能指回原文的那一句话；同一件事在多个来源出现时只算一次。

**产品原则（按优先级，冲突时上位覆盖下位）：**

1. **只报事实，不下定性。** 不出现“必须处理”“重要”这类标签。
2. **判断权归用户。** 系统可以排序、可以建议，不能替用户决定什么重要。
3. **排序必须可解释。** 每条“建议先看”都附一句可核对的理由。
4. **未识别的必须可见。** 不能被折叠、省略或默认隐藏——藏起来等于默认它不重要。
5. **一条信息只出现一次。** 同一事件多来源合并，并说明合并了什么。
6. **任何时候都能回到原文。**
7. **数据留在本机。** 不上云、不写进 Git。

## 3. 用户与场景

**第一目标用户：**同时使用 Moodle、学校邮箱和 Ed 的 Monash 本科生（当前以计算机相关专业为主，英语授课、中文母语）。

**使用场景：**

- 一天一到两次，课间或晚上，在笔记本上打开，几十秒内确认“有没有漏掉的变化”。
- 看到想处理的条目，点开详情，需要时跳回原文核对。
- 高峰是截止日前一周和期中。
- 判断顺序（这是学生自己的顺序，不是系统的分类）：这条跟我有关吗 → 是教学人员说的吗 → 它改变了我原本的计划吗 → 我要做什么。

**约束：**

- 邮件、课程记录、考勤属于敏感数据。
- SSO、MFA、会话过期会影响首次使用。
- 不同来源的时间字段、作者身份和内容结构不可直接比较。
- AI 不得把学生猜测写成学校正式要求。

## 4. 问题与证据

**问题：**学生分别打开四个平台，逐条判断“跟我有关吗、是老师说的吗、改变我原计划了吗、我要做什么”。漏事通常不是因为信息没送到，而是因为变化藏在四个地方，要逐条翻才知道哪条变了。

**已有证据**（2026-10-28 第一轮只读回放）：

- 最近 7 天共 39 封邮件、68 个 Ed 主题；
- Ed 主题中 7 个由教学人员发起、61 个由学生发起；
- 39 封邮件中 24 封未被现有规则归属到具体课程；
- 出现同一提醒分别从 Ed 和邮件发出、但标题不一致的情况。

这些只证明信息量、来源混杂和语义重复确实存在，**尚未证明**产品已经节省时间或避免遗漏。

## 7. 核心体验：自上次查看

主入口回答五个问题：

1. 自上次打开，一共变了多少条？
2. 分别来自哪个源，各多少条？
3. 哪些是系统能识别的（结构化变更）？
4. 哪些是系统没识别到的？
5. 只想先看几条的话，建议看哪几条，为什么？

```text
连接数据源
→ 后台同步
→ 检测结构化变更（新增 / 截止日改动 / 成绩发布 / 新文件 / 新帖与回复）
→ 按来源计数，按可核对的事实排序
→ 输出“自上次查看”的变更记录，附 1–3 条建议先看及理由
→ 用户展开任意来源或未识别区，逐条查看
→ 必要时打开原文，或标记不重要 / 不是给我的
```

聊天可以作为后续辅助入口，例如追问“这周 FIT1047 作业要求有什么变化”，但不是第一版主界面。

## 8. 功能需求

### FR-1 连接来源与首次设置

- **做什么：**Gmail / Ed / Moodle 各授权一次，此后后台自动同步。OnTrack 复用同一套凭据。
- **怎么用：**首次打开自动进入设置向导，逐个连接；连上之后不再出现。
- **现状：**已实现（Gmail OAuth、Ed token、Moodle 登录助手）。

### FR-2 同步状态

- **做什么：**每个来源上次同步时间、成功或失败、失败原因。
- **怎么用：**平时是一行小字；失败时能点“重新同步”，并明确缺的是哪个源。
- **现状：**已实现。

### FR-3 变更检测

- **做什么：**对每个条目保存字段快照，前后对比得出变更（新增、标题、截止时间、地点、成绩、附件、回复）。**这是确定性程序，不是模型判断。**
- **怎么用：**用户无感；变更直接进入 FR-4。
- **现状：**后端 `item_changes` 表已具备，写入链路需确认覆盖全部字段。

### FR-4 变更记录

- **做什么：**只列出变化，不重复陈列没变的内容。
- **怎么用：**打开首页就是它；每条可点开详情；看完可以“标记为已查看”。
- **现状：**进行中。当前简报按 `importance` 分组，需改为按变更类型与来源组织。

### FR-5 按来源计数

- **做什么：**每个来源各有多少条变化。
- **怎么用：**点数字展开该来源的条目，再点一次收起。
- **现状：**计划（现有来源筛选是平铺的 Segmented，不是计数）。

### FR-6 未识别区

- **做什么：**系统无法解析的原文段落单独归集并标注“未能识别”。
- **怎么用：**默认可见，可展开逐条看原文；**不允许被折叠藏起来**。
- **现状：**计划。需要先定义“解析失败”的判定口径，否则会变成第二个垃圾桶。

### FR-7 排序与建议先看

- **做什么：**按可核对事实排序（截止日临近、作者身份、是否已读）；最多 3 条“建议先看”，每条附一句理由，措辞为“可能”。
- **怎么用：**出现在最前面；不认同可以忽略，系统不因此改变排序。
- **现状：**计划。

### FR-8 条目详情与证据

- **做什么：**原文关键句、作者及身份、时间、跳回原文的链接。
- **怎么用：**点任意一条打开；返回后列表位置不丢。
- **现状：**已实现（详情抽屉 + 证据引文 + 原文跳转）。

### FR-9 用户标记

- **做什么：**已读、不重要、不是给我的、已提交。
- **怎么用：**在条目上直接标；标了“不重要”的不再出现在首页，但能在“全部”里找回。
- **现状：**已实现（`corrections`、`reads` 表）。语义需按新原则复核：标记是用户的判断，系统不得覆盖。

### FR-10 截止时间与资料

- **做什么：**按 `dueAt` 分组倒计时；每周资料按板块归类，可批量下载。
- **怎么用：**`/deadlines` 看倒计时；`/materials` 找资料。
- **现状：**已实现。没有结构化截止时间就不显示，不猜。

### FR-11 考勤

- **做什么：**识别考勤班次并填写代码。
- **怎么用：**`/attendance` 查看班次；默认只填不提交，需显式确认才提交。
- **现状：**已实现。这是唯一的写入型操作，权限与确认必须保持最严。

### FR-12 搜索与筛选

- **做什么：**按来源、课程、时间范围、关键词。
- **怎么用：**默认收起，需要时打开；`Cmd/Ctrl+K` 可全局跳转。
- **现状：**已实现（当前工具栏控件偏多，需要在改版中收敛）。

### FR-13 数据控制

- **做什么：**全部数据存在本地，可查看、可清除。
- **怎么用：**在设置里；清除前二次确认。
- **现状：**已实现（`DELETE /api/data`）。

### FR-14 MCP 只读接入

- **做什么：**把本地数据以只读 MCP 暴露给用户自己的 Agent。
- **怎么用：**技术用户在设置里拿到连接方式。
- **现状：**已实现，只读。

## 9. 页面规格：BriefPage（`/`）

把第 7 节的原则落到具体页面上。**截至本版，这一节只是规格，代码尚未按此实现**——现有页面仍按旧的 `importance` 分五组。

### 9.1 区块与顺序

从上到下七块，缺一块视为未完成：

1. **页头**：日期、视图切换（自上次查看 / 全部）、同步、标记本次已查看。
2. **建议先看**（≤3 条）：标题 + 一句可核对的理由。
3. **按来源计数**：Gmail / Ed / Moodle / OnTrack 各多少条，可点击筛选。
4. **变更记录**：字段级前后对比（截止时间、标题、课程、正文），一行一条。
5. **本次新增**：窗口内新增条目，按时间倒序，一行一条，不分组。
6. **没能归到课程**：`course` 为空的条目，默认展开。
7. **过去的内容**：窗口之外，默认折叠，每次展开 20 条。

### 9.2 数据来源与空态

| 区块 | 数据来源 | 为空时 |
|---|---|---|
| 建议先看 | 由条目事实计算（见 9.3） | 整块不渲染，不留空白 |
| 按来源计数 | `items.source` 计数 | 显示四个 0，不隐藏 |
| 变更记录 | `item_changes` 表 | 显示“自上次查看没有字段级变更” |
| 本次新增 | `items`（窗口内） | 显示“这段时间没有新增内容” |
| 没能归到课程 | `items.course === ""` | 整块不渲染 |

**关于“未识别区”**：第 8 节 FR-6 定义的未识别区，需要后端给出“解析失败”的信号，目前没有这个信号。第一版用 `course` 为空作为代理，界面上直接叫“没能归到课程”，不叫“未识别”——避免把课程归属失败说成内容解析失败。后端补上解析失败信号后，两者再合并。

### 9.3 排序与建议规则

“建议先看”按以下优先级取，最多 3 条，同一理由最多出现一次，不足就少放：

1. 有 `dueAt` 且距现在 ≤ 48 小时 → 理由“截止时间在 48 小时内”
2. 变更记录中存在 `due_at` 字段改动 → 理由“截止时间刚被改过”
3. `authorRole === "staff"` → 理由“教学人员发布”

除这三条规则外，不得引入任何模型打分的排序。列表本身按时间倒序，不按模型判断重排。

### 9.4 明确不做

- 不按 `importance` 分组，不显示“必须处理 / 重要 / 参考 / 折叠”；
- 不显示 `actionRequired`（需要行动 / 待确认）；
- 不提供按“类型”筛选——类型本身来自模型判断；
- 不在列表行上显示模型给出的任何定性标签。

### 9.5 验收

- 任一区块为空时，页面不塌陷，也不出现空卡片；
- 三条建议都能在详情里找到对应的原文证据；
- 变更记录每条都能点开对应条目；
- “没能归到课程”默认可见，不需要先展开；
- 断网时页头与空态正常，不弹错误框。

### 9.6 与现有实现的差距

| 区块 | 现状 | 要做 |
|---|---|---|
| 页头 | 有，但带三个计数牌 | 删掉计数牌，副标题改成一句话 |
| 建议先看 | 无 | 新增 |
| 按来源计数 | 来源是平铺的 Segmented，无数字 | 改成带计数的可点击条目 |
| 变更记录 | 有，但默认折叠、位置靠后 | 提为主区块 |
| 本次新增 | 按五个注意力层级分组 | 改为单一时间序列 |
| 没能归到课程 | 无 | 新增 |
| 过去的内容 | 有 | 保留 |

## 10. 数据模型

SQLite 表：`sources` / `items` / `item_content` / `item_changes` / `corrections` / `reads` / `sync_cursors` / `settings`。

本版的两条结论：

- **`item_changes` 是新模型的基础**——变更检测已经有地方落，不需要新建结构。
- **`items.importance` 和 `items.action_required` 要退役。** 它们承载的正是被取消的定性判断。退役前先确认没有页面继续读取，避免改一半。

## 11. 非功能需求

- **本地优先：**服务只绑 `127.0.0.1`，凭据在 macOS Keychain，正文与纠错只在本机，不进 Git、不上云。
- **安全：**状态变更请求检查 Origin；返回 CSP / nosniff / referrer 头。
- **可访问性：**正文对比度 ≥ 4.5:1，大字号 ≥ 3:1；键盘可达，焦点可见；不依赖颜色单独传达状态。
- **性能：**首页在 1 秒内可读；同步是后台任务，不阻塞界面。
- **语言：**界面中文；课程代码、标题、原文引用保留英文原样。

## 12. 范围边界

**P0（第一版）：**

- 本地 Web 入口与首次连接；
- 三源只读同步与同步状态；
- 自上次查看的变更记录（含按来源计数、未识别区、建议先看）；
- 变更详情、关键原句和原文跳转；
- 用户标记与本地数据查看/清除。

**P1（后续候选）：**OnTrack 纳入变更流、个性化排序、课程规则解释、日历与提醒、辅助问答、MCP/CLI 技术入口、桌面壳正式发布、真实用户测试。

**明确不做：**

- 以聊天框为主体的通用 Agent；
- 单纯的日历或截止日期提醒器；
- 对单条内容自动判定“必须处理”或“重要”；
- 自动完成、提交作业或代表用户发消息；
- 多学校、住房、签证和校园社区；
- 当前阶段的增长、付费和内容运营。

## 13. 指标

以下均为**目标**，不是当前结果。

| 指标 | 口径 |
|---|---|
| 变更检出率 | Gold Set 中应有变更的条目，被正确识别为变更的比例 |
| 漏报率 | 应有变更但未出现变更记录的条目比例（比检出率更重要的反向指标） |
| 排序命中率 | “建议先看”中，用户实际点开或标记为有用的比例 |
| 未识别覆盖率 | 未识别区中的内容，被用户展开查看的比例 |
| 原文跳转正确率 | 跳转链接能落到正确原文段落的比例 |
| 自用频率与时长 | 每天打开次数、从打开到关闭的时长（验证“几十秒”是否成立） |

不以“重要性分类准确率”作为指标——产品不再输出重要性分类。

## 14. 风险与开放问题

**风险：**

- **不判断的代价：**用户可能还是要全读。唯一补偿是排序可解释 + 未识别区可见；这两点任一做不好，产品就退回“只是换个地方翻”。
- **未识别区变成垃圾桶：**如果解析失败判定口径太宽，这一区会塞满内容，用户三次之后就永久忽略。
- **旧模型残留：**`importance` 字段和简报分组改一半，会出现两套并存的判断逻辑。
- **桌面壳未签名：**当前 macOS 包需要手动绕过 Gatekeeper，不能作为正式分发渠道。

**开放问题：**

- 107 条/7 天的信息量，是否足以让目标用户持续使用？
- 排序依据是否足够可解释，能被接受为“建议”而不是“判断”？
- 系统无法识别的占比会有多高，用户愿不愿意自己展开？
- Ed 学生主题的排序维度（课程、教师回复、热度、当前任务）如何取舍？
- Moodle assessment 的时间字段表示截止时间，不能与邮件、Ed 的发布时间直接比较；统一时间模型怎么设计？
- 桌面壳是 P1 还是砍掉，取决于本地 Web 是否已经够用。
