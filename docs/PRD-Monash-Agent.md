# Monash Agent 精简 PRD

> 版本：v0.1
>
> 日期：2026-10-28
>
> 状态：第一步产物，属于可修改的决策草案；第二步完成功能优先级后更新范围

## 1. 摘要

Monash Agent 面向需要同时检查 Moodle 和学校邮箱、但不愿配置 GitHub、CLI 或 MCP 工具的 Monash 学生。它把分散信息转化为可确认、可追溯、有优先级的行动事项，让用户在一个地方知道“需要做什么、什么时候完成、判断依据在哪里”。

第一版不做通用聊天助手，也不追求接入所有平台。它先跑通“同步信息—识别行动—展示依据—用户确认—本地提醒”的闭环。

## 2. 负责人

这是独立产品项目。项目所有者负责产品定义、方案取舍和最终交付；第三方开源工具和 AI 辅助产出必须单独标明，不能写成个人独立完成。

## 3. 背景

已有 Monash 开源工具可以读取 Moodle、Ed、OnTrack 等数据，但多数以 CLI、MCP 或单点插件存在。普通学生需要先知道这些项目存在，再理解 GitHub、运行环境、认证和配置方式。即使完成安装，不同工具仍缺少统一的事项状态、来源、确认、提醒和完成流程。

项目已经验证 Moodle、Ed、OnTrack 和 Gmail 的真实读取能力，也完成了相关生态、许可证和隐私边界调查。当前缺口不是继续增加连接器，而是把已有能力组织成普通用户能够直接完成任务的产品。

现阶段仍未通过真实用户研究证明需求强度。因此，“非技术学生存在明显安装门槛”“统一行动列表比单纯信息聚合更有价值”均作为待验证假设保留。

## 4. 目标

### 产品目标

让用户无需命令行操作，即可从 Moodle 和学校邮箱获得一个有来源、有状态、可以确认和提醒的学业行动列表。

### 第一阶段成功标准

以下均为目标，不是当前已完成结果：

1. 用户可以在匿名演示模式中，从同步数据到确认一个行动事项，完整走通核心流程。
2. 所有展示给用户的日期、规则和行动结论都能回到原始来源；无来源内容不得作为事实展示。
3. 建立不少于 50 条匿名化样本的初始评测集，并分别报告行动项识别、日期提取和重复合并的基线结果。

真实用户完成率、留存和遗漏规避次数，等具备用户验证条件后再加入，不提前假设。

## 5. 目标市场与用户

### 第一目标用户

需要反复查看 Moodle 和 Monash 学校邮箱，但不熟悉 GitHub、命令行和 MCP 配置的学生。他们希望减少平台切换，并快速判断哪些信息需要采取行动。

主要约束：

- 学校账号、邮件和课程记录属于敏感数据；
- SSO、MFA 和会话过期会影响首次使用；
- 用户可能不愿把数据上传到第三方服务器；
- 不同课程的信息格式和规则不一致；
- 当前用户需求与设备偏好仍缺少外部验证。

### 后续用户

希望通过 MCP、CLI 或 API 将 Monash 数据接入自有 Agent 的技术用户。该入口复用相同的数据模型，但不属于普通用户 MVP 的主界面。

## 6. 价值主张

- **Who：**需要同时检查 Moodle 和学校邮箱、但不想配置技术工具的 Monash 学生。
- **Why：**他们需要及时知道哪些信息要求行动，以及截止时间和依据是什么。
- **What before：**手动打开多个平台，阅读公告和邮件，再把重要事项复制到日历、Todo 或依靠记忆。
- **How：**产品自动同步结构化与非结构化信息，生成带来源的行动候选，由用户确认后进入提醒与完成流程。
- **What after：**用户可以从统一列表完成判断和安排，不必自己维护多个工具和重复整理信息。
- **Alternatives：**Moodle Dashboard、学校邮箱、个人日历、Notion，以及需要手动配置的 CLI/MCP 工具。Monash Agent 的差异是低门槛的一体化行动闭环，而不是更多信息。

**价值主张：**Monash Agent 不替学生完成学习任务，而是把学校分散的通知变成可信、可执行的行动，让用户少检查平台、少重复整理，并保留对每个结论的控制权。

## 7. 解决方案

### 7.1 核心流程

```text
连接 Moodle 和学校邮箱
→ 同步近期课程信息
→ 生成行动候选
→ 合并重复事项
→ 展示日期、风险和原始依据
→ 用户确认、修改或忽略
→ 创建本地提醒
→ 用户标记完成
```

### 7.2 第一版关键能力

1. **低门槛连接：**用可理解的界面引导授权，展示同步进度和失败原因，不要求用户执行命令。
2. **统一行动模型：**把 Moodle 的结构化日期和邮件中的非结构化行动要求转换为统一事项。
3. **证据优先：**每个关键结论保留原始来源；来源冲突时同时展示，不静默选择。
4. **用户确认：**AI 产生的是候选，不是最终事实。用户可以确认、修改、忽略和反馈错误。
5. **本地状态与提醒：**保存事项状态，避免重复提醒；不自动提交作业或发送消息。

### 7.3 AI 应用边界

| 类型 | 第一版职责 |
|---|---|
| 确定性程序 | 登录与同步、结构化 Moodle 日期、稳定 ID、状态保存、提醒调度、来源链接和精确重复判断 |
| AI 辅助 | 从邮件或公告提取行动候选、课程、日期线索和简短理由；识别语义重复；辅助风险分类 |
| 用户决定 | 确认、修改、忽略、完成；处理来源冲突；决定是否创建提醒 |

第一版不需要微调模型，也不建立万能 RAG 问答。模型必须可替换，产品价值主要来自数据接入、统一工作流、来源约束和纠错闭环。

### 7.4 假设与开放问题

- Moodle 与学校邮箱是否同时进入第一版，将在功能优先级阶段最终确认；当前方案倾向同时保留，因为两者分别提供结构化事实和非结构化 AI 场景。
- 桌面应用、Web 或其他入口尚未最终决定；选择应服从低门槛和隐私目标。
- 风险等级的定义、提醒渠道和日期冲突规则仍需设计。
- 用户是否愿意授权学校账号、是否真正需要统一行动列表，尚未通过外部用户验证。
- 当前先通过历史数据回测和匿名样本评测验证可行性；用户访谈与问卷不阻塞产品原型。

## 8. 发布边界

### 第一版

- 一个普通用户可以操作的入口；
- 最多两个数据源；
- 一个统一行动列表；
- 事项详情与原始证据；
- 确认、修改、忽略、完成和本地提醒；
- 匿名演示模式和初始 AI 评测集。

### 后续版本候选

- Ed、OnTrack 和更多来源；
- Monash 课程规则库和后果计算；
- MCP/CLI 技术用户入口；
- 更完整的提醒策略和跨源冲突处理；
- 经批准后的真实用户测试。

### 明确不做

- 通用 AI 聊天助手；
- 自动完成或提交作业；
- 多学校、住房、签证和校园社区；
- 当前阶段的增长、付费和内容运营；
- 为匹配 JD 而增加无关的 Dify、Coze 或多 Agent 功能。
