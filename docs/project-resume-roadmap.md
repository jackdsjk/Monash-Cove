# Monash Agent 项目与简历证据路线图

> 日期：2026-10-28
>
> 原则：每一步必须产生可检查的产品成果和可核验的简历证据；计划目标不能提前写成结果。

## 总体定位

该项目在三段项目组合中主要承担：

1. **通用产品能力：**问题定义、竞品分析、需求取舍、MVP、交互和迭代；
2. **AI 产品能力：**AI 边界、人工确认、来源约束、评测和 Bad Case；
3. **AI 开发能力：**多源接入、结构化处理、状态、异常与可测试性，作为产品落地支撑。

运营、增长和商业化暂不进入当前路线。

## 五个大步骤

| 步骤 | 主要问题 | 使用 Skill | 产品产物 | 简历证据 | 状态 |
|---|---|---|---|---|---|
| 1. 产品定义 | 为谁解决什么问题，AI 为什么必要 | `create-prd`、`ai-product-strategy` | 精简 PRD、AI 边界、文档事实源 | 问题定义、用户与替代方案、AI/规则/人工取舍 | **已完成初版** |
| 2. MVP 取舍 | 第一版到底做什么、不做什么 | `prioritize-features` | 功能池、评分表、P0/P1、决策记录 | 优先级、成本与风险权衡、砍功能能力 | 下一步 |
| 3. AI 评测 | 如何证明 AI 可靠且能迭代 | `ai-evals` | Gold Set、指标、Bad Case、基线报告 | 评测体系、错误归因、模型/规则迭代 | 未开始 |
| 4. 产品实现 | 如何形成可用、可演示的闭环 | 后续安装 UI 与测试 Skills | 可操作 MVP、匿名 Demo、E2E 测试 | 0→1 交付、体验设计、可靠性 | 未开始 |
| 5. 求职包装 | 如何把事实转成不同岗位信号 | `career-ops` project 模式 | One-pager、2 分钟 Demo、Postmortem、简历版本 | STAR 故事和量化结果 | 未开始 |

## 第一步：产品定义

### 本步结论

- 产品不是另一组 Monash 插件，而是把现有能力编排成普通学生能够使用的行动工作流。
- 第一目标用户暂定为需要检查 Moodle 和学校邮箱、但不熟悉命令行和 MCP 的学生。
- 产品核心是“统一行动事项 + 原始证据 + 用户确认 + 状态和提醒”。
- AI 只处理非结构化提取、语义去重和辅助分类；确定性事实、状态和高风险操作不交给模型独立决定。
- 技术用户的 MCP/CLI 接口保留为后续入口，不主导第一版体验。

### 已产生的证据

- 当前精简 PRD；
- 现有 GitHub 生态与许可证调查；
- Moodle、Ed、OnTrack、Gmail 的接入验证记录；
- 对“发现、安装、工作流”三层断裂的产品判断；
- 来源优先、冲突展示和永不自动提交的信任原则。

### 完成门槛

能够在 90 秒内回答：目标用户是谁、现有方案哪里断裂、第一版提供什么价值、AI 为什么只放在这些环节、哪些功能明确不做。

## 第二步：MVP 取舍

本步不直接开始写界面，而是先对候选功能评分。至少比较：

- Moodle 与 Gmail 数据源；
- 授权和同步；
- 统一事项模型；
- 行动项识别；
- 日期提取；
- 精确与语义去重；
- 风险分类；
- 来源展示；
- 用户确认和纠错；
- 本地提醒；
- Ed、OnTrack、规则库、AI 对话和 MCP 入口。

输出必须明确：

- P0 功能及其对应的用户价值；
- 被砍掉或延后的功能及原因；
- 第一版唯一核心流程；
- 每个 P0 功能的完成标准；
- 技术风险和产品假设分开记录。

完成后，更新 PRD 的第一版范围。

## 第三步：AI 评测基线

围绕真实产品任务建立不少于 50 条匿名化样本，至少覆盖：

- 是否需要行动；
- 课程识别；
- 截止日期；
- 行动类型；
- 重复事项；
- 来源是否支持结论；
- 高风险误判和漏判。

输出一份基线报告，分别说明规则、模型和人工确认处理了什么。后续每次改模型、提示词或规则，都必须对相同样本回归。

## 第四步：可操作产品与 Demo

进入该步骤时安装：

- `frontend-design`：确定产品界面和交互方向；
- `web-design-guidelines`：审查界面、可访问性和状态反馈；
- `playwright-best-practices`：覆盖核心流程和失败场景。

本步交付：

- 不使用命令行即可完成核心任务的 MVP；
- 不含私人数据的匿名演示模式；
- 两分钟内可展示价值的 Demo；
- 登录、同步、识别、确认、提醒和错误状态测试；
- 一次基于测试或回测结果的真实迭代。

## 第五步：简历和面试包

### 产品经理版本重点

- 为什么需求存在；
- 为什么选择该目标用户；
- 如何分析竞品和替代方案；
- 为什么选择这些 P0、砍掉哪些功能；
- 如何通过测试或数据改变第二版。

### AI 产品版本重点

- 为什么这些环节使用 AI；
- 如何处理概率性输出；
- 如何建立 Gold Set、指标与 Bad Case；
- 如何通过来源、人工确认和降级控制风险。

### AI 开发版本重点

- 多源适配和统一数据模型；
- 批量、分页、幂等、认证和异常处理；
- 结构化输出、规则与模型协作；
- 自动化测试和可替换边界。

### 最终求职交付

1. 一页项目说明；
2. 两分钟 Demo；
3. 项目复盘；
4. 产品经理版简历表述；
5. AI 产品版简历表述；
6. AI 开发版补充表述；
7. 可回答的面试问题与真实数据口径。

## 当前简历边界

目前可以证明的是生态调研、接入验证、产品判断、可信度设计和 Gmail 适配开发。当前还不能声称已经完成独立应用、获得用户、提高留存、避免遗漏或取得付费。

项目材料中的检索数量、技术结果和代码贡献，在进入正式简历前还需要由项目所有者确认自己能够解释，并区分本人实现、AI 辅助和第三方依赖。

## Career Ops 当前判断

**Verdict：BUILD。** 当前版本已经从“包装 CLI”转向“统一行动工作流”，具备较强的产品与 AI 产品故事。主要短板是没有可操作 Demo、评测基线和真实迭代；后续四步都直接针对这三个缺口。
